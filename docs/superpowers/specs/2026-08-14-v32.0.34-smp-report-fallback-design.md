# v32.0.34 SMP Report Fallback Design

## Goal
Make a closed historical month such as `2026_07` fully usable for analysis and reporting when local P1/HomeWizard detail data is missing or partial but SlimmeMeterPortal (SMP) has complete month coverage. A successful historical report must also appear in the existing user-facing report tree `Data/02_Output/Rapportages/YYYY_MM`.

## Proven problem
- The July workflow can finish `completed` while analysis still reports `Geen bruikbare bronbestanden: 2026_07` because `_month_energy_metrics()` only reads `P1e.csv`, `P1g.csv` and `Enphase.csv` from the local month-input folder.
- Historical report generation is deliberately skipped when `report_input_readiness()` sees those detail files as incomplete, even though SMP coverage for July is complete.
- The existing durable report package tree used by the project is `Data/02_Output/Rapportages/YYYY_MM`; `2026_08` exists there, while `2026_07` is missing.

## Architecture
Introduce one central SMP month-metrics reader and make both the analysis layer and report adapter consume the same resolved energy metrics. Do not manufacture fake `P1e.csv`/`P1g.csv` files.

### 1. SMP source resolution
For a requested month, search only these known project locations, in this order:
1. `Data/01_Input/YYYY_MM/HomeAssistant/SlimmeMeterPortal`
2. `Data/01_Input/YYYY_MM/SlimmeMeterPortal` (legacy July layout)
3. `/config/output/YYYY_MM` (local import evidence)

A source is eligible for closed-month fallback only when `content_coverage_report.json` has `status == "ok"`, `missing_days == []`, `empty_days == []`, and `available_through` equals the last calendar day of the requested month.

### 2. SMP metric extraction
Read the raw daily JSON files under `raw/`; do not rely on the current flattened monthly CSV because the current importer serializes the nested `usages` list and its numeric summary therefore does not expose the consumption fields.

For every `payload["usages"]` item:
- Electricity import: use numeric `delivery` when present; otherwise use `delivery_high + delivery_low`.
- Electricity export: use numeric `returned_delivery` when present; otherwise use `returned_delivery_high + returned_delivery_low`.
- Gas: use numeric `delivery` for the gas connection; when unavailable, fallback to the documented delivery reading delta only if both a first and last valid cumulative reading exist.

Never add a combined field and its high/low components together. This prevents double counting.

The reader returns a typed result with at least:
- `status`: `ready | incomplete | unavailable | error`
- `source`: `SlimmeMeterPortal`
- `source_root`
- `coverage_status`
- `grid_import_kwh`
- `grid_export_kwh`
- `gas_m3`
- `days_expected`
- `days_covered`
- `errors`

### 3. Source precedence and no double counting
For each metric independently:
1. Use P1/P1g when the local metric is available and its month coverage is accepted by the existing month-input validation.
2. Otherwise use SMP only when the SMP closed-month coverage gate is fully green.
3. Never sum P1 and SMP for the same metric.

The quality block records the chosen source per metric, e.g. `grid_import_source: p1` or `grid_import_source: slimmemeterportal_fallback`.

### 4. Analysis integration
`_month_energy_metrics()` uses the central resolved metrics. `available_sources` includes `SlimmeMeterPortal` whenever SMP supplies at least one accepted month metric. Therefore a complete SMP-only July month no longer triggers `Geen bruikbare bronbestanden`.

Existing Enphase logic remains unchanged. If Enphase is absent, solar-production-derived KPIs stay explicitly fallback/unknown according to the current safeguards; SMP never pretends to measure solar production.

### 5. Historical report readiness
`report_input_readiness()` gets a historical mode. A historical report is ready when the core energy metrics needed by the report adapter are available through either valid P1/P1g or complete SMP fallback. Missing historical socket files, Enphase or current-live-only sources do not by themselves skip the report.

The workflow keeps its current rule that historical processing never creates live snapshots for the old month.

### 6. Report adapter
`build_report_adapter_data()` consumes the same central resolved metrics as analysis. This guarantees dashboard/analysis and PDF report totals cannot diverge merely because they used different source selection logic.

The report metadata includes the energy source decision so a July report can be audited as `SlimmeMeterPortal fallback` for import/export/gas.

### 7. User-facing output location
On successful report generation, publish the durable report package to:
`Data/02_Output/Rapportages/YYYY_MM`

For July the required result is:
`Data/02_Output/Rapportages/2026_07`

Do not remove or overwrite unrelated existing reports. Publishing for the same month is idempotent and only replaces the exact generated files for that month after successful generation and checksum validation.

### 8. July repair behavior
After v32.0.34 installation, July does not need the full 11-step month workflow again. The system may run a targeted historical report rebuild for `2026_07` using the already validated SMP evidence. This rebuild must not:
- start or finalize August;
- enable automatic month closure;
- call a standalone/manual `finalize_month` action;
- collect live snapshots for July;
- alter existing July SMP raw evidence.

The durable July completion marker remains valid; v32.0.34 repairs analysis/report output, not the already completed month workflow.

## Error handling
- Incomplete SMP coverage: do not use SMP as authoritative fallback; leave the metric unavailable or use valid P1 if available.
- Malformed raw JSON or non-numeric usage values: record an explicit source error and do not silently convert missing values to zero.
- Mixed P1/SMP availability: resolve each metric separately and report the chosen source.
- Report build failure: do not create/replace the durable `Rapportages/YYYY_MM` package.

## Tests
TDD coverage must include:
1. RED/GREEN: complete SMP-only July yields import/export/gas metrics and `available_sources` contains `SlimmeMeterPortal`.
2. P1 wins when valid P1 and SMP are both present; no double counting.
3. Partial SMP coverage is rejected as fallback for a closed month.
4. Raw usage parser uses `delivery` instead of also adding `delivery_high/low`; same for returned delivery.
5. Historical `report_input_readiness()` becomes ready with complete SMP core metrics even when P1/HomeWizard/Enphase detail files are absent.
6. Report adapter and analysis return the same import/export/gas totals for the same SMP-only fixture.
7. Successful targeted July report build creates `Data/02_Output/Rapportages/2026_07` with the expected report artifacts.
8. Failed report generation leaves any existing durable month report package untouched.
9. August state/finalization is unchanged by the targeted July report rebuild.
10. Full existing suite remains green and release identity/changelog/manifests are updated to `32.0.34` only after behavior tests pass.

## Scope exclusions
- No change to automatic month-closure scheduling.
- No automatic iCloud upload.
- No new HomeWizard history synthesis.
- No changes to Crash Recovery behavior.
- No change to NextEnergy contract logic.

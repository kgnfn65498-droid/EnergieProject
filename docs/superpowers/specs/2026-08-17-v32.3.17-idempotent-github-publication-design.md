# v32.3.17 Idempotent GitHub Publication Design

## Goal

Remove the stale Home Assistant GitHub publication loop that appears when the project-standard release path has already merged the target release to GitHub MAIN before the validated ZIP is installed live.

## Root cause

The installer correctly creates a fail-closed publication contract with `expected_previous_version` and the previous manifest. The HA publisher previously accepted only that previous GitHub baseline. In the project-standard route, however, MAIN is intentionally already on the target release before the definitive ZIP is delivered. The publisher therefore rejected the valid state `remote version == target version` forever and retried every polling interval.

## Required behavior

The publisher distinguishes four remote states:

1. `previous`: version and previous manifest exactly match the contract. Existing publication flow continues unchanged.
2. `target_exact`: target version and target manifest match, and the remote files validate against that manifest. Publication is already complete; remove the contract without another push.
3. `target_source_match`: target version is already present and all source files match the validated target release, ignoring only generated release metadata `MANIFEST.sha256` and `SHA256SUMS.json`. Synchronize the validated release source so final metadata is published, then use the existing push/remote verification and contract cleanup.
4. `mismatch`: any real source difference, unexpected version or invalid manifest remains fail-closed. No overwrite or force push.

## Safety

- Never accept target-version equality alone.
- Exact target requires the remote manifest to validate the actual remote files.
- Metadata-only recovery requires a complete source fingerprint match excluding only the two generated metadata files.
- Existing processed-ZIP SHA, staged target-manifest validation, SSH key checks, no-force-push rule and post-push remote verification remain unchanged.
- Operating modes, RELEASE VALIDATION HOLD, Crash Recovery, watcher, scheduler and month-close semantics do not change.

## Verification strategy

Pre-delivery publication verification remains mandatory. Testing becomes risk-guided rather than blindly repetitive:

- During development: focused tests first.
- Always before MAIN: one complete source regression suite after final code changes.
- Always before ZIP delivery: publication-contract/idempotence tests plus ZIP integrity/manifest checks and one complete regression suite from a fresh ZIP extraction.
- Escalate automatically to additional installer/simulation/full repeats when a test fails unexpectedly or when release, recovery, mode, installer or destructive paths change.
- Do not repeat equivalent full-suite runs merely to duplicate evidence.

## Exit criteria

- Previous-baseline flow still passes.
- Prepublished target with metadata-only difference passes and can finish publication.
- Exact target is idempotently accepted only after manifest-to-files verification.
- Same target version with any real source difference is rejected.
- Full regression suite and final ZIP verification are green.

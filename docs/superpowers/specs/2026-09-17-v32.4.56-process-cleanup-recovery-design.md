# v32.4.56 Process/Cleanup/Recovery Design

## Goal

32.4.56 consolidates transient development/test/cache material under one canonical `Inbox/process` workspace, makes CLEARUP manage only proven-safe process debris and known legacy root debris, preserves reversible quarantine semantics, keeps Crash Recovery max-1 per CR type, and hardens Projectmanager startup/live-acceptance recovery after the 32.4.55 incident.

## Boundaries

- Canonical top-level live structure remains `App`, `Backups`, `Inbox`, `Data`, `Infra`, and `CLEARUP`.
- Temporary test/build/cache material belongs under `Inbox/process`; do not create new root-level temporary namespaces.
- CLEARUP remains hard-move quarantine with manifest and restore path. No destructive delete capability is added.
- Release rollback retention remains 3; Crash Recovery retention remains 1. These are different domains.
- EnergieProject CR and NAS Containers CR must keep the previously proven create/verify-first, then keep-1 behavior.
- The current 32.4.55 mode-readback fix and HA persistent-notification cleanup are part of the base and must not regress.

## Process workspace

Create a small shared module with a canonical root `Inbox/process` and namespaces `tmp`, `cache`, and `active`. A JSON process map records registered transient artifacts. Only registered `tmp`/`cache` artifacts that are explicitly released or stale may become CLEARUP candidates. Unknown/unregistered process debris is health debt but is not automatically moved.

The process map is an operational namespace and is protected from blanket CLEARUP. It is written atomically using the existing shared Runtime-compatible file-mode contract.

## Root hygiene

Extend structural hygiene to recognize canonical root directories and classify known root release/build debris. Existing rollback policy stays keep-3. Known failed releases, excess rollbacks, root release ZIP leftovers, and narrowly matched temporary/build artifacts are candidates for reversible CLEARUP. Unknown root material is reported as debt and remains fail-closed.

## Crash Recovery retention

No policy rewrite: assert and preserve max-1 for EnergieProject CR and NAS Containers CR. A regression test must fail if either active route drifts away from keep-1. Do not alter Home Assistant internal backup retention.

## Embedded Projectmanager/live acceptance

32.4.55 proved that the primary GUI can run while the embedded Projectmanager stops publishing fresh status. 32.4.56 adds explicit startup-cycle observability and a bounded recovery state machine. It must detect a missing fresh PM cycle after add-on startup, record evidence, and may request at most one Supervisor restart of the Energie add-on within a 60-minute durable window after the 15-minute grace period. It never restarts the whole Home Assistant host, never touches release state to fabricate progress, and a second stale boot in the same window fails closed as BLOCKED. No fake COMPLETE/ACCEPTED state may be written.

The recovery boundary is therefore the Energie add-on itself, not the Home Assistant host; the durable restart budget prevents a restart loop.

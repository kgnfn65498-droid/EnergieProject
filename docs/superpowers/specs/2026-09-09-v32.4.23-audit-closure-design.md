# EnergieProject v32.4.23 Audit Closure Design

**Approved basis:** audit/overdracht 2026-09-09 plus explicit user command `maak 4.23`.

## Goal
Close the remaining 32.4 safety/governance gaps without changing the proven atomic swap, watcher or GitHub publisher behavior.

## 1. Canonical month-closure truth
A single pure predicate classifies RecoveryManager data as `CLOSED_VALID`, `OPEN`, or `UNKNOWN`.
`CLOSED_VALID` requires `status=CLOSED`, validation `ok`, verification `valid`, `deep_verified=true`, and no `hash_failures`.
A valid MCP response with `closed=false` and no closure status file is `OPEN`; transport errors, malformed results, or an asserted CLOSED state lacking deep verification are `UNKNOWN`.
Automatic workflows fail closed on `UNKNOWN` and never execute a `CLOSED_VALID` month.

The `month_closure_status` MCP call bypasses the generic read cache so a transient `None` or stale OPEN result cannot become permanent runtime truth.

Independent guards are applied in scheduler due calculation, automatic preflight and executor before any RUNNING retry state or workflow mutation is written.

## 2. Startup readiness
`STARTUP_RECOVERY_READY` is set only after startup recovery returns a semantically safe status and the previous-month closure truth is not `UNKNOWN`.
Otherwise automatic scheduling stays disabled and the problem remains visible in logs/state.

## 3. Production core certification
`PRODUCTION_CORE_REVISION` is raised because scheduler/preflight/executor semantics change.
Release validation becomes certificate-aware. A current valid certificate passes. A core-revision mismatch is reported as pending and may not allow automatic month-closing; no old certificate may silently certify new core behavior.
The release hold records this condition explicitly and remains fail-closed for automatic mutation.

## 4. Roadmap semantic governance
Canonical roadmap validation rejects dependency cycles.
For the current canonical roadmap it also verifies mandatory pre-32.5 gates are present and are transitive dependencies of `cowork-pilot`.
The approved canonical roadmap migration records: ngrok is retained and must be secured; `voice-live-acceptance` and `new-chat-handover-live` occur before 32.5/Cowork.
Self-audit validates semantic correctness, not only hash/version synchronization.

## 5. External PM ingress for ngrok
Do not expose all of port 8099 as a public API.
Add a dedicated external PM conversation route only. It is deny-by-default unless an edge secret is configured. The server verifies, using constant-time comparison, an edge-injected secret plus an allowed authenticated principal and client identifier. The request body cannot choose its own trusted identity/source channel; the server maps authenticated client identity to `chatgpt`, `voice`, or `nomad`.
Secrets are read only from environment and never written to project data.
Rate limiting and OAuth/OIDC remain ngrok edge policy and are configured only after 32.4.x closure.

## 6. Testing and packaging
Every production change starts with behavior tests that fail on 32.4.22, then GREEN implementation, focused regression, complete suite where sandbox execution permits, static/package checks, fresh-extract tests, manifest/SHA validation, and release identity checks.
Documentation/KB/roadmap lessons are updated in the release artifact.

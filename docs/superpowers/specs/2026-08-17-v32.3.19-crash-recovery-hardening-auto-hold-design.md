# v32.3.19 Crash Recovery Hardening + Automatic HOLD Release Design

## Goal

Finish the pre-vacation safety chain by making Crash Recovery cooperate completely with the operating-mode controller and by removing the routine manual RELEASE VALIDATION HOLD click after a healthy release.

## Scope

1. **Automatic HOLD release after install/restart**
   - RELEASE VALIDATION HOLD is still armed fail-closed by the installer before publication/startup.
   - The running add-on automatically executes the exact existing five release checks plus measured reconciliation.
   - Only a fully green validation may call the existing normal `release_hold` path.
   - Any blocked/failed validation leaves HOLD active. No emergency release is ever automatic.
   - Automatic retries are bounded/backed off; a persistent problem remains visible and the manual button remains available as fallback.

2. **Crash Recovery backup/verify isolation**
   - Starting backup/verify temporarily switches USER or DEVELOPMENT to MAINTENANCE.
   - While that session is active, `schedule`, `full_workflow` and `automatic_month_close` are suspended so no new automatic month/workflow mutation starts during backup/verify.
   - An already active workflow makes Crash Recovery return busy/failed-safe; it is not force-killed by this change.
   - Safe success and safe failure return to the exact original USER/DEVELOPMENT base and preserve DEVELOPMENT-session state.

3. **Crash Recovery cleanup owns its MAINTENANCE window**
   - After a completed browser download, cleanup itself starts a `mutating_maintenance` session before it queues the watcher cleanup request.
   - The mode remains MAINTENANCE while the watcher request is pending, so the watcher is actually allowed to process it.
   - A matching watcher result `ok` closes the temporary session and returns to the original base mode.
   - A watcher cleanup failure is treated as an unsafe partial maintenance outcome and keeps MAINTENANCE active for inspection.
   - Restart while cleanup is pending preserves MAINTENANCE and resumes reconciliation; restart during an unclassified mutating operation remains unsafe/fail-closed.

## Non-goals

- No changes to USER/DEVELOPMENT/MAINTENANCE base semantics.
- No changes to release watcher ingress policy.
- No destructive restore automation.
- No retention cleanup yet; that follows only after a new verified Crash Recovery set exists.
- No Home Assistant Core update handling.

## Exit criteria

- Automatic healthy release validation releases HOLD without user click.
- Any failed release check leaves HOLD active.
- Backup/verify disables all three automatic mutation capabilities while MAINTENANCE is active and restores the exact original mode afterwards.
- Post-download cleanup enters MAINTENANCE, remains there until the watcher result is known, then returns on `ok` or stays MAINTENANCE on unsafe failure.
- Restart behavior for backup/verify and pending cleanup is deterministic and fail-safe.
- Full source suite, definitive MAIN ZIP suite, installer simulation and targeted mode/HOLD/Crash-Recovery gates are green.

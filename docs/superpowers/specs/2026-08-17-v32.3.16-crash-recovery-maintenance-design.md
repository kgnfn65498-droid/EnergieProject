# v32.3.16 Crash Recovery Maintenance Integration

## Goal

Make the operating-mode controller complete for the current project scope by integrating Crash Recovery with temporary MAINTENANCE mode while preserving the user's original base mode.

This release is deliberately small. It does not redesign Crash Recovery, restore logic, cleanup policy, watcher gating, scheduler behavior, or month-close behavior.

## Required mode behavior

Crash Recovery always records the current base mode before entering temporary maintenance.

### Started from USER

`USER -> temporary MAINTENANCE -> Crash Recovery/verification -> USER`

### Started from DEVELOPMENT

`DEVELOPMENT -> temporary MAINTENANCE -> Crash Recovery/verification -> DEVELOPMENT`

The base mode itself is not rewritten when Crash Recovery starts. DEVELOPMENT therefore remains an active development session and cannot be ended by Crash Recovery.

## Success and failure semantics

### Successful backup/verification

- Enter temporary MAINTENANCE.
- Perform Crash Recovery backup and verification.
- Record `CRASH_RECOVERY = PASS`.
- Reconcile actual runtime/state.
- Clear the temporary maintenance transition.
- Return to the exact original base mode.

### Ordinary safe failure

Examples: backup creation fails, ZIP validation fails, checksum verification fails, read-only restore preview fails, or another operation fails before any unsafe mutation is left behind.

- Record `CRASH_RECOVERY = FAILED` with reason.
- Reconcile state.
- Clear temporary maintenance.
- Return to the exact original base mode so development or normal user operation can continue.

### Unsafe partial mutation

Only operations that can leave production state partly changed qualify, for example a restore, destructive cleanup, migration, or infrastructure mutation that cannot prove complete rollback.

- Record `CRASH_RECOVERY = UNSAFE` with explicit reason/evidence.
- Keep effective mode in MAINTENANCE.
- Do not auto-return to USER or DEVELOPMENT.
- Require a later verified recovery/repair action before leaving MAINTENANCE.

## Durable Crash Recovery mode session

Use a durable session record under writable runtime state, for example:

`Inbox/operating_mode/crash_recovery_session.json`

It records at minimum:

- schema version
- session/request id
- original base mode
- original effective mode
- original `development_session_active`
- transition id
- operation class (`backup_verify` or `mutating_maintenance`)
- phase/status
- started/completed timestamps
- outcome (`pass`, `failed_safe`, `unsafe`)
- failure/unsafe reason

The protected Projectmanager state directory is not used for writable runtime session state.

## Crash/reboot recovery

A restart must not lose the original mode.

- An interrupted `backup_verify` session is treated as a safe failed backup unless evidence says a mutating step started; on the next controller/recovery pass it records failure and restores the original base/effective mode.
- An interrupted `mutating_maintenance` session remains MAINTENANCE until its rollback/recovery state is explicitly proven safe.
- DEVELOPMENT stays persistent across the restart when it was the original base mode.

## Integration boundary

The Crash Recovery entry/exit path must use the existing operating-mode state machine instead of directly editing mode-state JSON fields.

The integration must not change:

- USER / DEVELOPMENT / MAINTENANCE profile semantics
- RELEASE VALIDATION HOLD rules
- DEVELOPMENT explicit-close rule
- scheduler or automatic month-close logic
- release watcher ingress gating
- destructive restore/delete gates

## Report-service history retention

Change `report_service_retention_months` from 3 to **13 months** (1 year + 1 month) in the current release configuration/default and matching tests/documentation.

This is report-service history only. The general month-data retention remains unchanged.

## Backup/cleanup retention scope

v32.3.16 does **not** delete accumulated backups or other project files.

After v32.3.16 passes live mode validation, the next Crash Recovery run must first create and verify a fresh recovery set. Only after that fresh recovery set is green may Projectmanager audit:

- `Backups`
- release/pre-release backups
- processed release ZIPs
- RestoreStaging remnants
- relevant project-manager/system run folders
- other project folders with obvious temporary/duplicate material

The audit first produces a preview/classification (`BEHOUDEN`, `VERWIJDERBAAR`, `ONZEKER`) and recommended retention values. Destructive cleanup happens only after the fresh recovery set is proven and the cleanup scope is safe.

The known watcher/container values `ENERGIE_BACKUP_RETENTION=999` and `ENERGIE_PROCESSED_RETENTION=999` are therefore an audit target after the fresh Crash Recovery set; they are not silently changed before that backup exists.

## Acceptance tests

v32.3.16 is not complete until all of these are proven:

1. USER -> temporary MAINTENANCE -> successful backup/verification -> USER.
2. DEVELOPMENT -> temporary MAINTENANCE -> successful backup/verification -> DEVELOPMENT.
3. DEVELOPMENT session remains active throughout #2.
4. Safe backup failure from USER returns USER and records FAILED.
5. Safe backup failure from DEVELOPMENT returns DEVELOPMENT and records FAILED.
6. Unsafe partial mutation remains MAINTENANCE and records UNSAFE.
7. Reboot during `backup_verify` restores the original base mode with failed-safe evidence.
8. Reboot during unresolved mutating maintenance remains MAINTENANCE.
9. No mode transition can end DEVELOPMENT without explicit user confirmation.
10. Existing RELEASE VALIDATION HOLD, scheduler, watcher, month-close and reconcile safety tests remain green.
11. `report_service_retention_months` default/configuration is exactly 13 and cleanup keeps the latest 13 report-service months.
12. Full regression suite is green before packaging.

## Exit criterion

If the tests above and one non-destructive live mode handoff test are green, set:

`MODES_EXIT = PASS`

No additional operating-mode release is required for the current scope. The project then moves directly to creation, verification and retention-audit of the new Crash Recovery set.

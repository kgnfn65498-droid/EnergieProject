# v32.3.15 GUI action navigation design

## Scope

Small usability release on top of the validated v32.3.14 operating-mode controller. No change to mode semantics, release hold rules, scheduler behavior, automatic month-close behavior, watcher gating, or Projectmanager safety policy.

## Problem

The operating-mode controls in the Home Assistant Ingress Web UI currently POST to action endpoints and return a raw JSON response. Inside Home Assistant Ingress the normal browser Back button is not a reliable way to return to the Energieproject page. The user therefore has to reopen the Web UI after every action.

## Chosen behavior

GUI form actions use a Post/Redirect/Get flow:

1. User clicks a control such as DEVELOPMENT, Reconcile, Release-hold valideren/vrijgeven, or another operating-mode action.
2. The server executes exactly the same underlying action and safety checks as today.
3. On success or handled error, the GUI request redirects back to the same Energieproject Web UI page instead of rendering raw JSON.
4. The returned page shows one short status banner describing the result, for example `DEVELOPMENT ingesteld`, `Reconcile OK`, `Release-hold vrijgegeven`, or a concise error.
5. Refreshing the page does not repeat the POST action.

## API compatibility

The underlying command/runtime functions continue returning their structured dictionaries exactly as before. Raw JSON remains available to technical callers/tests through the existing Python functions and any explicitly non-GUI/API route. Only POST requests originating from the rendered GUI forms receive redirect-and-banner behavior.

## Safety requirements

- No GUI navigation change may alter USER / DEVELOPMENT / MAINTENANCE semantics.
- DEVELOPMENT remains persistent until explicit user confirmation to end development.
- Release Validation Hold validation and emergency-release gates remain unchanged.
- A failed action must not be disguised as success; the redirected page must show an error banner.
- Redirect handling must remain within the Home Assistant Ingress path; no absolute external redirect URL.
- No automatic workflow, month close, release processing, or scheduler action is introduced by this change.

## UI clarification

While touching this card, remove the ambiguity discovered during v32.3.14 validation. The card must distinguish the mode profile from measured runtime during HOLD. Suggested wording:

- `Basisprofiel maandverwerking: AAN/UIT`
- `Effectieve maandverwerking: AAN/UIT`

The effective value comes from the measured runtime snapshot. This is display-only and must not change controller behavior.

## Implementation boundary

Primary file: `slimmemeterportal_import/rootfs/app/operating_mode_web.py`.

A small helper may be added if needed for safe Ingress-relative redirects or flash-message encoding. Do not refactor unrelated Web UI/runtime code.

Because v32.3.14 is already live, this change is released as v32.3.15 rather than modifying the existing 32.3.14 artifact.

## Tests

Add focused tests for:

- successful GUI mode change redirects to the Energieproject page;
- successful reconcile redirects and displays a success banner;
- successful release-hold validation redirects and displays its result;
- handled errors redirect and display an error banner;
- refresh after redirect does not repeat the POST;
- redirect target is Ingress-relative and cannot escape the application path;
- raw underlying structured results remain available to non-GUI callers;
- card shows both basis-profile and effective runtime month-processing state;
- existing v32.3.14 mode/HOLD/runtime/installer tests remain green;
- full regression suite remains green before packaging.

## Acceptance criteria

The user can click any operating-mode control once and stay in the Energieproject Web UI without manually reopening it. The resulting page clearly confirms success/failure, does not replay the action on refresh, shows no raw JSON during normal GUI use, and preserves all v32.3.14 safety behavior unchanged.

# v32.3.15 GUI action navigation design

## Scope

Small usability release on top of the validated v32.3.14 operating-mode controller. No change to mode semantics, release hold rules, scheduler behavior, automatic month-close behavior, watcher gating, or Projectmanager safety policy.

## Problem

The operating-mode controls in the Home Assistant Ingress Web UI currently POST to action endpoints and return a raw JSON response. Inside Home Assistant Ingress the normal browser Back button is not a reliable way to return to the Energieproject page. The user therefore has to reopen the Web UI after every action.

## Chosen behavior

GUI form actions use a Post/Redirect/Get flow:

1. Every rendered operating-mode form includes hidden field `return_ui=1`.
2. User clicks a control such as DEVELOPMENT, Reconcile, Release-hold valideren/vrijgeven, or another operating-mode action.
3. The server executes exactly the same underlying action and safety checks as today.
4. For `return_ui=1`, success or handled error returns `303 See Other` to the same Home Assistant Ingress application page instead of rendering raw JSON.
5. The returned page shows one short status banner describing the result, for example `DEVELOPMENT ingesteld`, `Reconcile OK`, `Release-hold vrijgegeven`, or a concise error.
6. Refreshing the redirected GET does not repeat the POST action.

The redirect target is derived from the current Ingress request path and stays inside that application path. It never uses a user-supplied absolute URL.

## API compatibility

Requests without `return_ui=1` retain the existing JSON response contract. The underlying command/runtime functions continue returning their structured dictionaries exactly as before. This allows existing technical callers and tests to keep using the current behavior while normal GUI clicks use redirect-and-banner navigation.

## Status banner

The redirect carries only a short, URL-encoded notice code/value generated by the server. Banner text is selected from fixed server-side messages; arbitrary user input is not rendered as trusted HTML. The existing HTML escaping remains in force.

A success banner is informational only. An error banner must reflect the actual failed action and may not convert an error into a successful controller state.

## Safety requirements

- No GUI navigation change may alter USER / DEVELOPMENT / MAINTENANCE semantics.
- DEVELOPMENT remains persistent until explicit user confirmation to end development.
- Release Validation Hold validation and emergency-release gates remain unchanged.
- A failed action must not be disguised as success; the redirected page must show an error banner.
- Redirect handling must remain within the Home Assistant Ingress path; no absolute external redirect URL.
- No automatic workflow, month close, release processing, or scheduler action is introduced by this change.

## UI clarification

While touching this card, remove the ambiguity discovered during v32.3.14 validation. The card must distinguish the mode profile from measured runtime:

- `Basisprofiel maandverwerking: AAN/UIT`
- `Effectieve maandverwerking: AAN/UIT`

The basis-profile value comes from `desired_profile`. The effective value comes from `observed_profile.automatic_month_close_effective` when measured runtime is available; if it is unavailable, the UI must show `ONBEKEND` rather than infer a safe value. This is display-only and must not change controller behavior.

## Implementation boundary

Primary file: `slimmemeterportal_import/rootfs/app/operating_mode_web.py`.

A small helper may be added in that module for safe Ingress-relative redirects, notice encoding/decoding, and `303` response construction. Do not refactor unrelated Web UI/runtime code.

Because v32.3.14 is already live, this change is released as v32.3.15 rather than modifying the existing 32.3.14 artifact.

## Tests

Add focused tests for:

- rendered GUI forms include `return_ui=1`;
- successful GUI mode change returns `303` to the Energieproject page and displays a success banner;
- successful reconcile redirects and displays a success banner;
- successful release-hold validation redirects and displays its result;
- handled GUI errors redirect and display an error banner;
- refresh after redirect does not repeat the POST;
- redirect target is Ingress-relative and cannot escape the application path;
- POST calls without `return_ui=1` still return the existing JSON response;
- raw underlying structured results remain available to non-GUI callers;
- card shows both basis-profile and measured effective month-processing state;
- missing measured runtime is displayed as `ONBEKEND`;
- existing v32.3.14 mode/HOLD/runtime/installer tests remain green;
- full regression suite remains green before packaging.

## Acceptance criteria

The user can click any operating-mode control once and remain in the Energieproject Web UI without manually reopening it. The resulting page clearly confirms success/failure, does not replay the action on refresh, shows no raw JSON during normal GUI use, preserves JSON compatibility for non-GUI calls, distinguishes desired from measured runtime, and preserves all v32.3.14 safety behavior unchanged.

# v32.3.19 Crash Recovery Hardening + Automatic HOLD Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Automatically release a healthy post-install HOLD and make Crash Recovery own safe MAINTENANCE windows for backup/verify and asynchronous cleanup.

**Architecture:** Reuse the existing release validation and mode-session primitives rather than inventing parallel safety logic. Extend Crash Recovery sessions with explicit suspended features and a pending-cleanup phase reconciled by the existing controller worker; add a bounded automatic normal-HOLD validation worker that never uses emergency release.

**Tech Stack:** Python 3.12+, pytest, Home Assistant add-on runtime, QNAP watcher shell/Python cleanup helper.

## Global Constraints

- Existing USER/DEVELOPMENT/MAINTENANCE base semantics remain unchanged.
- DEVELOPMENT session may not be closed implicitly.
- RELEASE VALIDATION HOLD remains fail-closed and emergency release is never automatic.
- Crash Recovery safe success/failure returns to exact originating USER/DEVELOPMENT mode.
- Unsafe partial cleanup/restore remains MAINTENANCE.
- No retention deletion in this release.

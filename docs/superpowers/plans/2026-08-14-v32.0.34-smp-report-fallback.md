# v32.0.34 SMP Report Fallback Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a completed historical month with complete SlimmeMeterPortal evidence fully usable for analysis and reporting, and publish its durable report package under `Data/02_Output/Rapportages/YYYY_MM` without rerunning or finalizing the month workflow.

**Architecture:** Add one central SMP raw-month metrics resolver and use it from both `_month_energy_metrics()` and `build_report_adapter_data()`. Historical report readiness becomes metric-based rather than requiring live-detail CSVs. Durable report publication is an atomic, month-scoped copy after a successful local report build.

**Tech Stack:** Python 3.12, stdlib JSON/CSV/pathlib/shutil/hashlib, pytest, existing Home Assistant add-on/report service code.

## Global Constraints

- Release version is `32.0.34`; production core revision stays `9.4-core1`.
- P1/P1g wins when valid; SMP is fallback only and is never summed with P1/P1g.
- Closed-month SMP fallback requires complete green `content_coverage_report.json` through the calendar month end.
- Historical rebuild must not collect live snapshots, enable automatic month closure, alter August, or call standalone/manual `finalize_month`.
- Do not synthesize fake `P1e.csv`/`P1g.csv` files.
- Existing Crash Recovery and NextEnergy logic is out of scope.
- No GitHub Actions during development.

# v32.3.16 Crash Recovery Maintenance Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the current operating-mode scope by making Crash Recovery temporarily enter MAINTENANCE and restore the exact original USER/DEVELOPMENT base mode after safe success or safe failure, while preserving MAINTENANCE after an unsafe partial mutation and changing report-service history retention to 13 months.

**Architecture:** Add one focused `operating_mode_crash_recovery.py` coordinator beside the existing operating-mode modules. It owns the durable Crash Recovery mode-session record, enters/exits temporary MAINTENANCE through the existing `begin_temporary_mode()` / `end_temporary_mode()` state-machine functions, wraps the existing Crash Recovery entry points without changing their backup/restore implementation, and provides startup recovery before generic stale-transition recovery. Nested calls inside `run_complete_crash_recovery_export()` reuse the same session so MAINTENANCE spans backup, deep verify, RestoreStaging and export.

**Tech Stack:** Python 3.12, JSON/Path/threading already used by the add-on, pytest, Home Assistant add-on runtime, existing operating-mode state machine.

## Global Constraints

- USER / DEVELOPMENT / MAINTENANCE profile semantics do not change.
- DEVELOPMENT remains persistent and cannot end without explicit user confirmation.
- RELEASE VALIDATION HOLD, watcher gating, scheduler and automatic month-close behavior do not change.
- Crash Recovery from USER returns USER after safe success/failure.
- Crash Recovery from DEVELOPMENT returns DEVELOPMENT after safe success/failure and keeps the development session active.
- Unsafe partial restore/cleanup/migration state remains MAINTENANCE until separately repaired.
- Writable Crash Recovery mode-session state lives under `Inbox/operating_mode`.
- Report-service history retention is exactly 13 months; general month-data retention is unchanged.
- v32.3.16 performs no broad backup cleanup. Retention audit/cleanup starts only after a fresh verified Crash Recovery set exists.
- Release identity is exactly `32.3.16`.

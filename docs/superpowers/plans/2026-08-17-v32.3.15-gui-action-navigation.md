# v32.3.15 GUI Action Navigation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep Home Assistant Ingress users on the Energieproject Web UI after operating-mode actions, show a concise result banner, and clarify basis-profile versus measured effective month-processing state without changing v32.3.14 safety behavior.

**Architecture:** Keep all behavior in `operating_mode_web.py`. GUI forms opt in with `return_ui=1`; the POST handler executes the existing action unchanged, then returns an Ingress-relative `303 See Other` to `./?mode_notice=<fixed-code>&mode_level=<success|error>`. Normal callers without `return_ui=1` retain the exact JSON response. The rendered card contains a small client-side banner reader for those fixed query codes and displays both desired-profile and observed-runtime month-processing values.

**Tech Stack:** Python 3.12, `http.server`-style handler already used by the add-on, `urllib.parse`, pytest, Home Assistant Ingress.

## Global Constraints

- No change to USER / DEVELOPMENT / MAINTENANCE semantics.
- DEVELOPMENT remains persistent until explicit user confirmation to end development.
- No change to Release Validation Hold validation or emergency-release gates.
- No change to scheduler, automatic month close, watcher gating, release processing, or Projectmanager safety policy.
- Only GUI forms carrying `return_ui=1` receive redirect/banner behavior; existing structured JSON remains unchanged for all other calls.
- Redirects remain Ingress-relative; never accept a caller-supplied redirect URL.
- Status text is selected from server-owned fixed codes, not echoed from arbitrary user input.
- Release identity becomes `32.3.15`; v32.3.14 remains the current live baseline until this release is separately validated.

In `operating_mode_web.py`:

```python
from urllib.parse import parse_qs, urlencode, urlparse

_UI_NOTICE_CODES = {
    "development_set",
    "user_set",
    "maintenance_set",
    "auto_updated",
    "reconcile_ok",
    "release_hold_released",
    "emergency_release_done",
    "action_failed",
}


def _ui_redirect_location(notice_code: str, level: str) -> str:
    code = notice_code if notice_code in _UI_NOTICE_CODES else "action_failed"
    safe_level = "success" if level == "success" else "error"
    return "./?" + urlencode({"mode_notice": code, "mode_level": safe_level})


def _send_ui_redirect(handler, notice_code: str, level: str) -> None:
    handler.send_response(303)
    handler.send_header("Location", _ui_redirect_location(notice_code, level))
    handler.send_header("Cache-Control", "no-store")
    handler.end_headers()
```

Add hidden `return_ui=1` to each rendered GUI action form. In `wrapped_do_post`, parse `return_ui`, run the exact existing action first, then call `_send_ui_redirect(...)` only when `return_ui` is true; otherwise preserve the existing JSON `send_body` path byte-for-byte in semantics.

Use fixed notice selection by endpoint/result, e.g. DEVELOPMENT → `development_set`, reconcile → `reconcile_ok`, successful hold release → `release_hold_released`. In the exception block, redirect with `action_failed/error` only for GUI requests; non-GUI requests keep the current JSON 400 error.
